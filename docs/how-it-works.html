How it works

Instagram Content MCP Agent

A solo creator wants to post about "Embeddings" tonight, explained properly, not as a Wikipedia stub. That means a caption, an image that isn't a diagram, and both live on Instagram before the moment passes.

Three chores, three failure modes: an LLM that rambles, an image model that returns a cluttered infographic, a two-step Graph API upload that fails silently if the image isn't public yet. Doing this by hand every time is what kills the habit.

One pipeline turns a topic into a live post: an LLM writes the caption, an image model generates the visual, an MCP server exposes both plus the Graph API call as tools a LangChain coordinator calls in sequence, retrying automatically on each step.

03 MCP session opensagents/mcp_client.py spawns mcp_server/instagram_tools_server.py as a stdio subprocess and loads its 3 tools once, for the whole run, via langchain-mcp-adapters.
04 generate_contentThe Content Creator Agent calls the generate_content MCP tool, which runs ContentGenerator (gpt-4o-mini, structured output) and returns caption/bullets/hashtags; retried once on failure.
05 generate_imageThe Image Generator Agent calls generate_image, which runs ImageGenerator (Stability AI by default, with an OpenAI alternative and a placeholder-image last resort), saves a PNG to assets/, and returns its public URL; retried once.
06 post_to_instagramThe Instagram Poster Agent calls post_to_instagram, which maps format to a Graph API media_type, creates a media container, waits 2 seconds, and publishes it via Graph API v18.0 (or returns a dry-run stub); retried once.
07 Persist + respondThe route writes a ContentRequest and Post row to Postgres via SQLAlchemy, then returns the post ID, image URL, and full progress log to the frontend.

Key trade-offs›
  • LCEL over LangGraph: the coordinator is a plain RunnableLambda | RunnableLambda | RunnableLambda sequence, not a graph, because the flow never branches or cycles. The cost: there's no built-in support for running content and image generation in parallel, or for adding a human-approval branch later, without an actual rewrite onto a graph framework.
  • Placeholder image on total provider failure: when every image provider call raises, the pipeline substitutes a local "Image unavailable" PNG and still completes the run rather than failing it. That trades correctness for availability: a broken image API can result in an actually-published Instagram post with the wrong picture, instead of a visibly failed request.
  • Reels are rejected, not attempted: post_to_instagram maps format to the Graph API's media_type (STORIES for stories, omitted for a plain post), but a reel request returns an explicit error instead of publishing an image under the Reels label, because a REELS container needs a real video_url and this pipeline never generates video. The cost: the app genuinely cannot fulfill a "Reel" request right now, a real capability gap, not just a labeling detail, and the frontend has to disable that option rather than offer it and fail.
  • A fresh MCP subprocess per request: run_coordinator() opens a new stdio_client session (and spawns mcp_server/instagram_tools_server.py fresh) on every API call, rather than keeping one long-lived MCP server process. That keeps the client/server boundary genuinely real instead of simulated, at the cost of a subprocess spin-up and re-importing every tool's dependencies on each request.
Reflections›
Orchestration: LangGraph state graph, then plain LCEL›
  • Started with a LangGraph-style design: requirements.txt still carries langgraph as a dependency with a comment noting it "isn't imported by the app anymore," and the older docs (docs/MULTI_AGENT_ARCHITECTURE.md, docs/CODE_OVERVIEW.md) still describe a per-agent state dict and list "LangGraph - Agent workflow" as a core technology.
  • Stepped back because the workflow never branches or cycles: it is content, then image, then post, every single time. Graph nodes and edges were pure ceremony for what is actually a straight line.
  • Landed on a LangChain Expression Language RunnableSequence (the | operator) instead. It expresses the linear chain directly, and as a real bonus each step got .with_retry() for free, something the graph-based version never had.
Content generation: manual text parsing, then structured output›
  • Started with a raw ChatOpenAI call and manual text parsing, splitting the model's response on markdown bullets and section headers to pull out the caption, ingredients, and steps (per tools/content_generator.py's own module docstring).
  • Stepped back because that parsing broke whenever the model's formatting drifted: an extra intro sentence, a different bullet marker, a missing header, and the split logic would silently mis-parse the caption.
  • Landed on ChatOpenAI(...).with_structured_output(ContentSchema): caption, bullets, steps, and hashtags come back as typed, Pydantic-validated fields, so the model has to fill in the shape rather than the code guessing at it after the fact.
Image generation: fail the pipeline, then degrade gracefully›
  • Started from a single provider call that simply raised on failure, which meant one flaky Stability AI response threw away the already-completed, already-billed content-generation step and blocked a post that was otherwise ready to go.
  • Stepped back because "no post" felt like the wrong failure mode for something as replaceable as one image, especially once a retry had already been tried and failed.
  • Landed on a three-tier fallback: primary provider, then a secondary provider if one is configured, then a locally rendered placeholder image so the run still completes. This is a genuine trade-off, not a free win (see Key trade-offs): it exchanges a visible failure for a post that goes out looking wrong.
Prompting: one generic template, then topic-aware routing›
  • Started wanting a single prompt template that worked for any topic, whether it was "Embeddings" or "Ragi Dosa Recipe" (both real example topics from the codebase).
  • Stepped back because a recipe and a technical topic need genuinely different caption structure: ingredients plus numbered steps versus a hook plus explained bullets. One template produced a generically-shaped result for both.
  • Landed on _is_recipe_topic(): a keyword match against the topic and topic details routes to one of two prompts and system messages, and _assemble_caption() formats the result differently (Ingredients:/Recipe: headings for food, plain bullets and numbered steps otherwise).
Run it›

Content generation defaults to OpenAI's gpt-4o-mini; image generation defaults to Stability AI's stable-diffusion-xl-1024-v1-0 (set IMAGE_PROVIDER=openai to switch). Instagram requires the generated image at a public HTTPS URL, so a tunnel (ngrok) is needed for the poster step to succeed outside dry-run mode. That URL is only known after the tunnel starts, so PUBLIC_IMAGE_SERVER_URL gets added to .env after the ngrok step below, not before it. Requires Python 3.10+ (the mcp package's actual floor, per its published metadata; nothing in requirements.txt states this explicitly) and Node 20.19+/22.12+ (Vite 7's minimum, per frontend/package.json's vite: ^7.2.2); both pip install -r requirements.txt and npm install were run against the actual manifests in this repo to confirm a clean install.

git clone <repo url>
cd instagram-content-mcp-agent
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# create .env in the project root with:
#   OPENAI_API_KEY, STABILITY_API_KEY,
#   INSTAGRAM_ACCESS_TOKEN, INSTAGRAM_ACCOUNT_ID, DATABASE_URL

python scripts/setup_database.py
scripts/start_image_server_and_ngrok.sh   # prints a public ngrok URL

# add that URL to .env as PUBLIC_IMAGE_SERVER_URL, then:
uvicorn backend.main:app --reload         # http://localhost:8000/docs

cd frontend && npm install && npm run dev  # http://localhost:5173

Dry-run mode (on by default in the frontend) skips the two real Graph API calls, but it doesn't skip the tunnel requirement: InstagramPoster.post_image rejects a file:// image URL before it ever checks dry_run, so without PUBLIC_IMAGE_SERVER_URL set the pipeline still fails at the posting step, just with a local validation error instead of a real Instagram API call.
